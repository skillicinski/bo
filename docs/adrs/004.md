# ADR-004: Single Manifest, Materialized Views, and Write-Intent Recovery

**Status:** Accepted
**Date:** 2026-05-19
**Supersedes:** none
**Audit history:** original draft 2026-05-16; revised 2026-05-19 to fix unsafe rollback, eliminate bidirectional cross-reference drift, scope staleness to deletion, drop migration scaffolding, drop schema version field, clarify single-writer model.

---

## Context

Bo's tree state is currently spread across multiple files:

- `{tree}/.bo/index.jsonl` — append-only leaf roster (URL, title, filename)
- `{tree}/.bo/state.json` — compile timestamp
- `{tree}/branches/` directory — branch existence discovered by filesystem scan
- Individual file frontmatter — authoritative per-entity metadata

This works but has compounding problems:

1. **No single source of truth.** Tree topology is reconstructed by joining index + filesystem scan + frontmatter reads. Status, compile, and query all re-derive the same state differently.
2. **No crash safety.** A compile that writes 3 branch files and updates 10 leaf frontmatter entries can fail mid-way, leaving the tree inconsistent with no recovery path.
3. **Branch metadata is invisible to the index.** Incremental compile needs to know which branches exist, which leaves they contain, and whether they're stale — information that currently requires scanning the branches directory and parsing every branch's frontmatter.
4. **Schema evolution is painful across multiple files.** Adding a field to the index requires migrating JSONL parsing; adding branch tracking requires a new file format entirely.

Iceberg-style manifest files and Kimball's One Big Table pattern demonstrate that for datasets well below millions of rows, denormalization into a single manifest eliminates join complexity, simplifies schema evolution, and maps cleanly to future storage backends without relational overhead.

---

## Decision

### 1. Single normalized manifest

All tree topology and metadata lives in `{tree}/.bo/manifest.json`. This file is the single source of truth for what exists in the tree, how entities relate, and what state they're in.

The manifest stores the **normalized core data model**. Cross-references between entities use slugs (stable identifiers), not inlined copies. **Each cross-reference has exactly one canonical direction** — the inverse is computed in-memory at point of use, never serialized. This eliminates the possibility of mirrored fields drifting out of sync.

**Canonical direction:** `BranchRecord.leaves` lists the leaf slugs assigned to that branch. The inverse (which branches a leaf belongs to) is derived in-memory.

**The manifest replaces:** `index.jsonl`, `state.json`, and filesystem scanning of the `branches/` directory.

**The manifest does NOT replace:** the actual `.md` content files. Content lives on disk as markdown; the manifest tracks structure and metadata.

### 2. Single-writer concurrency model

Bo is single-writer-per-tree-per-machine. Two concurrent `bo` processes mutating the same tree produces undefined behavior. This is enforced by an advisory lock: a non-stale `pending.json` causes new mutating commands to refuse to start.

This constraint is independent of intra-process concurrency. A single `bo collect urls.txt` run is free to fan out network fetches asynchronously; only the manifest write is serialized.

### 3. Write-intent recovery

Every mutating operation follows a write-ahead pattern:

1. Compute pre-mutation manifest hash.
2. Write `{tree}/.bo/pending.json` describing the intended mutations and their target content hashes.
3. Stage content writes to temporary paths (e.g., `branches/foo.md.tmp`).
4. Rename staged files into place (atomic per-file).
5. Write updated `manifest.json` (atomic via tmp + rename).
6. Delete `pending.json`.

Step 5 is the commit point: the new manifest either reflects the new state or it doesn't. Recovery uses content hashes from `pending.json` to disambiguate which staged writes landed before the crash.

## Manifest Schema

```rust
/// {tree}/.bo/manifest.json
///
/// Normalized core data model. Cross-references are unidirectional:
/// branches list their leaf slugs; the inverse is computed in-memory.
/// Rewritten atomically on every mutation.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Manifest {
    pub tree: TreeMeta,

    /// All collected leaves. Vec, not map — iteration order is stable
    /// (insertion order = collected_at). Slug lookups are linear but
    /// the list is small enough that this doesn't matter (<1000 entries).
    pub leaves: Vec<LeafRecord>,

    /// All compiled branches.
    pub branches: Vec<BranchRecord>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct TreeMeta {
    pub name: String,
    pub created_at: String,
    /// Set on successful compile. None if never compiled.
    pub last_compiled_at: Option<String>,
}

/// A leaf record. No back-reference to branches — that's derived in-memory.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct LeafRecord {
    pub slug: String,
    pub file: String,
    pub title: String,
    pub url: String,
    pub collected_at: String,
    #[serde(default)]
    pub summary: Option<String>,
}

/// A branch record. Owns the canonical leaf-membership list.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct BranchRecord {
    pub slug: String,
    pub file: String,
    pub title: String,
    pub compiled_at: String,

    /// True when one or more leaves referenced by this branch no longer exist
    /// in `manifest.leaves`. Set by compile or by a future `bo status` audit.
    /// Modification staleness (leaf content changed since compile) is out of scope.
    #[serde(default)]
    pub stale: bool,

    /// Slugs of leaves assigned to this branch. Canonical direction.
    pub leaves: Vec<String>,
}
```

### Schema evolution

Non-breaking additions use `#[serde(default)]`. Old manifests deserialize cleanly. Breaking changes (field removal, type changes) will introduce an explicit version field at that time; we don't pay for it speculatively.

### Resolution helpers

```rust
impl Manifest {
    pub fn leaf_by_slug(&self, slug: &str) -> Option<&LeafRecord> { ... }
    pub fn branch_by_slug(&self, slug: &str) -> Option<&BranchRecord> { ... }
    pub fn uncompiled_leaves(&self) -> Vec<&LeafRecord> { ... }
    pub fn stale_branches(&self) -> Vec<&BranchRecord> { ... }
    pub fn leaves_for_branch(&self, branch_slug: &str) -> Vec<&LeafRecord> { ... }
    /// Computes inverse cross-reference at call time. Not stored.
    pub fn branches_for_leaf(&self, leaf_slug: &str) -> Vec<&BranchRecord> { ... }
}
```

`uncompiled_leaves` is computed by collecting all leaf slugs not present in any `BranchRecord.leaves`. Linear over branches × leaves; trivial at target scale.

### Architectural stance: normalized domain, denormalized views

The manifest stores the normalized domain model. **Denormalization is a property of consumers, not of storage.** Each operation materializes the view it needs at the point of use:

| Consumer | Materializes |
|----------|-------------|
| `bo compile` (LLM prompt) | Resolved view: branch structure + full leaf summaries |
| `bo query` (retrieval) | Context window: relevant leaf content + branch summaries |
| `bo status --json` | Projection: counts, staleness, hints derived from records |
| Branch `.md` files | Persistent artifact: synthesised prose; frontmatter is a regenerable projection of the manifest |

Branch frontmatter is **not** a source of truth. The manifest is canonical for branch metadata. Hand-edits to branch frontmatter will be overwritten on the next compile that touches that branch. No divergence-detection feature is planned — the asymmetry is intentional.

## Write-Intent Schema

```rust
/// {tree}/.bo/pending.json
///
/// Exists on disk only during an active mutation. Presence = incomplete operation.
/// Doubles as an advisory lock against concurrent bo processes on the same tree.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct PendingOperation {
    pub op: OpKind,
    pub started_at: String,
    /// Process ID of the bo invocation that wrote this file.
    /// Used by lock-staleness checks to detect crashed processes.
    pub pid: u32,
    /// SHA-256 of manifest.json bytes before the operation (hex).
    /// Used by recovery to determine if mutations partially landed.
    pub pre_manifest_hash: String,
    /// Files this operation intends to write (relative to tree root).
    pub writes: Vec<PendingWrite>,
    /// Files this operation intends to delete.
    #[serde(default)]
    pub deletes: Vec<String>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "type")]
pub enum OpKind {
    Collect { url: String },
    Compile { mode: CompileMode },
    Raze { include_auth: bool },
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum CompileMode {
    Incremental,
    Full,
    RebuildStale,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct PendingWrite {
    /// Final path relative to tree root (not the staging path).
    pub path: String,
    /// SHA-256 (hex) of the intended new content. Used during recovery to
    /// distinguish "staged write landed" from "pre-existing file".
    pub content_hash: String,
}
```

### Recovery logic

On startup of any mutating command, if `pending.json` exists:

1. Compute current SHA-256 of `manifest.json`.
2. **If `current_hash == pre_manifest_hash`** (manifest never updated → operation crashed before commit):
   - For each `write` in `pending.writes`:
     - Remove the staging file `{path}.tmp` if present.
     - Hash the file at `path`. If it equals `pending.content_hash`, the staged write was renamed into place but the manifest never committed; revert the file (delete if it didn't pre-exist, restore from the prior content if available — see below).
     - If the hash does not equal `content_hash`, the file is either pre-existing or untouched; leave it alone.
   - For each `delete` in `pending.deletes`: leave alone (the manifest didn't commit, so the file should still exist; if it doesn't, it was already deleted by the crashed run and there's nothing we can do).
   - Delete `pending.json`. Warn the user.
3. **If `current_hash != pre_manifest_hash`** (manifest updated → operation completed but crashed before deleting `pending.json`):
   - Delete any leftover `.tmp` staging files referenced by `pending.writes`.
   - Delete `pending.json`. No data loss.

**Rollback caveat:** for "staged write landed but manifest didn't commit," fully restoring the prior file content requires backing up the original before rename. v0.0.2 does not implement backup — the recovery action is "delete the file that shouldn't be there." This is correct for new files (collect creating `slug.md`) but lossy for overwrites (compile rewriting `branches/foo.md`). The mitigation: compile always writes a fresh `branches/foo.md.tmp` and only renames after the manifest commits — so for compile, the prior `branches/foo.md` is still on disk if the crash happens before manifest commit. The rename-then-commit ordering means at most one file is in the "staged but not committed" state at any moment.

To make this safe, **the rename-into-place step happens after the manifest write, not before.** Updated flow:

1. Compute pre-manifest hash.
2. Write `pending.json`.
3. Stage all content writes to `*.tmp` paths.
4. Write `manifest.json` (atomic tmp + rename). **This is the commit point.**
5. Rename all staged `*.tmp` files into their final paths.
6. Apply deletes.
7. Delete `pending.json`.

Now the recovery cases collapse:

- **Manifest unchanged → crash before commit:** delete all `*.tmp` files listed in `pending.writes`. Final paths untouched.
- **Manifest changed → crash after commit, before final renames/deletes:** rename any remaining `*.tmp` files into place; apply remaining deletes; delete `pending.json`. Roll-forward to consistency.

Content hashes in `pending.json` are now optional belt-and-braces — the staging-then-rename ordering plus manifest-as-commit-point provides the safety. We retain `content_hash` because it makes roll-forward verifiable: a staged file whose hash matches `content_hash` is the one we wrote; mismatches indicate disk corruption and abort recovery with an explicit error.

### Advisory lock semantics

A `pending.json` whose `pid` is alive and whose `started_at` is within the last 60 seconds blocks new mutating commands with `tree busy: another bo process is mutating this tree (pid {pid})`. Outside that window, the file is treated as a crashed-run marker and triggers the recovery flow above.

## Operation Flows

### `bo collect <url>`

```
1. Acquire lock: check pending.json, recover if stale, refuse if live.
2. Read manifest.json; reject if url already in leaves[].url.
3. Compute pre_manifest_hash.
4. Write pending.json { op: Collect{url}, writes: [{path: "slug.md", hash}], pre_manifest_hash, pid }.
5. Stage {tree}/slug.md.tmp.
6. Write updated manifest.json (atomic).        ← commit point
7. Rename slug.md.tmp → slug.md.
8. Delete pending.json.
```

### `bo compile` (incremental)

```
1. Acquire lock.
2. Read manifest.json.
3. Compute uncompiled_leaves(); if empty and no stale branches: exit "nothing to compile".
4. Build LLM prompt: existing branch structure + new leaf summaries.
5. LLM call → validate response (item 2 of v0.0.2).
6. Compute pre_manifest_hash.
7. Write pending.json { op: Compile{Incremental}, writes: [branch tmps], pre_manifest_hash, pid }.
8. Stage branches/*.md.tmp for each new/updated branch.
9. Write updated manifest.json (atomic).        ← commit point
10. Rename branches/*.md.tmp → branches/*.md.
11. Delete pending.json.
```

### `bo compile --all`

Same flow; step 3 selects all leaves regardless of branch membership; step 8 stages overwrites for all existing branches.

### `bo compile --dry-run`

Builds the `PendingOperation` struct in memory, prints it, exits without touching disk. Never writes `pending.json`. Recovery semantics are unaffected.

### `bo status`

```
1. Read manifest.json (no lock — read-only).
2. Derive metrics from manifest:
   - Leaf count: manifest.leaves.len()
   - Branch count: manifest.branches.len()
   - Uncompiled: manifest.uncompiled_leaves().len()
   - Last compiled: manifest.tree.last_compiled_at
   - Stale branches: manifest.stale_branches().len()
3. Filesystem scan only for content size in bytes (the one metric the manifest doesn't track).
```

### `bo raze`

```
1. Acquire lock.
2. Compute pre_manifest_hash.
3. Write pending.json { op: Raze{include_auth}, deletes: [all tree files], pre_manifest_hash, pid }.
4. Delete content files.
5. Delete manifest.json.            ← commit point (manifest gone = tree gone)
6. Delete pending.json.
7. Delete config tree pointer (and ~/.bo/auth.json if --include-auth).
```

## Consequences

**Positive:**

- Single source of truth — all tree topology answered from one file read.
- Crash-safe mutations via stage-then-commit-then-rename: at most one `.tmp` file ever exists in an inconsistent state, and recovery is mechanical.
- O(1) file reads for status/compile planning except for content-size scan.
- Schema evolution via serde defaults — additive changes are free.
- Clean DB migration path — flat records with slug references, trivial junction table if needed.
- Enables incremental compile (manifest knows exactly what's uncompiled).
- Enables dry-run trivially via in-memory `PendingOperation` materialization.
- No bidirectional cross-reference drift (single canonical direction).

**Negative:**

- Slug resolution requires linear scan over Vec — irrelevant at target scale, O(1) HashMap upgrade available later.
- Manifest must be read into memory in full on every command — fine at <1MB; revisit at 10K+ entries.
- `bo collect` performs ~5 fs operations (read manifest, write pending, stage tmp, write manifest, rename, delete pending). Accepted: dwarfed by network fetch time.
- Branch content lives in .md files while branch metadata lives in manifest — two locations for one logical entity. Manifest is canonical; .md frontmatter is a regenerable projection.

**Neutral:**

- Loss of append-only semantics from JSONL — replaced by atomic rewrite + write-intent.
- Single-writer-per-tree-per-machine constraint. Documented and enforced by advisory lock.

## Out of Scope

- **Migration from v0.0.1 layout.** Bo has no users beyond the maintainer; v0.0.2 is a fresh-tree release. Old trees are rebuilt with `bo raze && bo seed`. No migration code path ships.
- **Schema version field.** YAGNI until a breaking change is needed; serde defaults handle additive evolution.
- **Modification-based staleness detection.** Requires content hashing leaves on collect; deferred. v0.0.2 only flags branches stale on leaf deletion.
- **Cross-process locking on networked filesystems.** The PID-based advisory lock assumes local filesystem semantics.
- **Backup/restore of pre-mutation file content.** Stage-then-commit makes this unnecessary for the operations bo currently performs.

---

## Alternatives Considered

1. **Extend `index.jsonl` with branch entries** — preserves append-only but doesn't solve crash safety, still requires filesystem scanning for branch metadata, and JSONL is awkward for updates/deletions.
2. **Fully denormalized manifest with inlined cross-references** (LeafRef/BranchRef types carrying full metadata of referenced entities) — eliminates lookups but creates consistency maintenance burden and provides no real benefit when the full manifest is loaded into memory anyway. Denormalization happens at materialization, not at storage.
3. **Bidirectional cross-references** (`LeafRecord.branches` mirroring `BranchRecord.leaves`) — was the original design. Rejected: storing both directions on disk reintroduces drift exactly where the architectural stance forbids it. The inverse direction is computed in-memory.
4. **SQLite from day one** — correct eventually but premature now. Adds a build dependency, complicates the "it's just files" mental model, and the manifest can migrate to SQLite later when scale demands it.
5. **Full WAL with separate redo log** — overkill for an interactive CLI. The single-pending-file model gives crash detection and roll-forward at a fraction of the implementation cost.

## References

- Write-ahead logging (WAL): intent-before-mutation for crash recovery, simplified to a single pending.json with stage-then-commit-then-rename.
