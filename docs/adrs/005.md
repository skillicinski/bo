# ADR-005: Deterministic Processing at LLM Boundaries

**Status:** Accepted  
**Supersedes:** None  
**Context:** Discovered during incremental compile dogfooding (May 2025)

## Decision

Deterministic operations at LLM call boundaries follow two rules:

1. **Pre-LLM:** Any state resolution whose outcome does not depend on the LLM's response must execute _before_ the call. This narrows the LLM's input to only what requires semantic judgment, reducing complexity and token cost.

2. **Post-LLM:** When a structured-output response violates a structural invariant that the caller can resolve deterministically, resolve it in code rather than retrying or failing.

The LLM is trusted for creative/semantic work (synthesis, concept identification, relevance judgment). It is **not** trusted for deterministic state management — even with explicit prompt instructions, JSON schema enforcement, and few-shot examples.

## Motivation

### The pre-LLM principle: narrow the input

During incremental compile, stale branch repair (removing deleted-leaf references from branches, dropping branches below 2-leaf minimum) was initially delegated to the LLM. The prompt marked branches as `stale="true"` and instructed the model to rebuild them.

This failed systematically:
- The operation is entirely deterministic — remove dead slug from leaf list, check count, keep or delete.
- The LLM consistently failed to address all stale branches, requiring a post-hoc code fallback.
- The fallback did exactly what should have happened before the call.
- The stale branch bodies and annotations consumed tokens without adding value.

**Fix:** `repair_stale_branches()` runs as a pre-pass. The manifest is written clean _before_ prompt construction. The LLM never sees stale annotations, never receives instructions about rebuilding, and only handles its actual semantic task: integrating new leaves into a clean branch structure.

This follows the principle Gulli describes in *Prompt Chaining*: the "insertion of deterministic logic between model calls" that "reduces the operational complexity for the large language model at each step." The insight here is that the deterministic step should happen _before_ the call, not between two calls — it's the same principle applied to input preparation rather than output routing.

More broadly, from the *Planning* chapter: "When a problem's solution is already well-understood and repeatable, constraining the agent to a predetermined, fixed workflow is more effective." Stale repair is well-understood and repeatable. It was never an LLM problem.

### The post-LLM principle: guardrails with deterministic repair handlers

Two systematic failures emerged across both `gpt-4o` and `gpt-4.1` in the LLM's actual semantic task (new-leaf integration):

#### Example 1: New branches referencing only existing leaves

**Invariant:** In incremental mode, every new branch must include at least one newly-collected leaf.

**Observed behaviour:** The model consistently reorganises existing branches (creates new branches from old leaves) while ignoring the new leaf — especially when the new leaf is topically isolated from the existing cluster.

**Prompt attempts that failed:**
- "Only output branches that include at least one new leaf"
- Explicit `<new_leaves_to_integrate>` section listing slugs
- "If none fit any concept, return empty arrays"
- All three combined

**Deterministic fix:** Silently drop new branches whose leaf list contains no new leaf. The useful branches pass through; the irrelevant reorganisations are discarded.

#### Example 2: Duplicate branch slugs in new_branches

**Invariant:** New branches must not duplicate slugs of existing branches.

**Observed behaviour:** The model places an existing branch in `new_branches` instead of `updated_branches`, causing a slug collision.

**Deterministic fix:** Detected at validation; the schema distinction (`updated_branches` has `slug`, `new_branches` doesn't) makes this a hard error because the LLM's intent is ambiguous. This is correctly a failure, not a repair — it violates principle 5 below.

## Principles

1. **Deterministic before statistical.** If an operation's outcome is known without the LLM's output, execute it first. The LLM receives a cleaner, smaller, more focused input. This reduces token cost, prompt complexity, and the surface area for model misbehaviour.

2. **Validate-then-fix, not validate-then-fail.** If a post-LLM violation is mechanically resolvable (drop, filter, repair), resolve it. Only fail on violations that require semantic understanding to fix (malformed bodies, contradictory content, ambiguous intent).

3. **Never retry for structural compliance.** LLM non-determinism means the same structural violation may recur indefinitely. Retrying wastes tokens and time. If the fix is deterministic, apply it on the first pass.

4. **Prompt for intent, enforce in code.** The prompt communicates what the ideal response looks like. The code enforces what the response must satisfy. These are different concerns — prompt quality is best-effort optimisation; code enforcement is the contract.

5. **The schema is necessary but not sufficient.** JSON schema prevents syntactic malformation. It cannot prevent semantic violations (wrong leaf references, reorganisation without integration, missing required entries). Post-parse validation + deterministic repair covers the gap.

6. **Log dropped content at debug level.** Silent drops should be observable for diagnostics but should not produce user-facing noise. The user sees the result, not the LLM's missteps.

## The compile pipeline as illustration

```
repair_stale_branches()  →  select_new_leaf_slugs()  →  LLM call  →  validate + filter
   (deterministic)            (deterministic)          (semantic)    (deterministic)
```

Each step operates at the appropriate level of trust. The LLM's responsibility is narrowed to one question: "where do these new leaves fit conceptually?" Everything else — staleness, deletion, structural compliance — is handled by code that can guarantee its answer.

This embodies Gulli's observation from the *MCP* chapter: "agents do not magically replace deterministic workflows; they often require stronger deterministic support to succeed." The deterministic support here isn't just scaffolding around the agent — it's active pre-processing that makes the agent's job smaller, clearer, and more likely to succeed on the first attempt.

## Applicability

**Pre-LLM deterministic processing** applies when:
- The operation's result depends only on current state (filesystem, manifest, config), not on LLM judgment
- The operation produces a cleaner/smaller input for the LLM
- Deferring it would require the LLM to handle it (poorly) and code to repair it (redundantly)

**Post-LLM deterministic repair** applies when:
- The caller knows the complete set of valid states (e.g., valid leaf slugs, existing branch slugs)
- The violation can be detected by comparing the response against known-good data
- A reasonable default exists (drop, filter, use existing value)
- The semantic content of the response is still useful after the repair

**Neither** applies when:
- The violation is in the creative output (bad synthesis, hallucinated content)
- No deterministic resolution exists (the response is fundamentally unusable)
- The repair would silently change the semantic meaning of the output

## Consequences

- Compile succeeds on the first attempt in all observed real-world scenarios (previously required 3–5 retries or model switching)
- Prompt engineering becomes optimisation (better results) rather than correctness (system doesn't break)
- Token cost decreases — deterministic operations don't consume LLM context
- The validation layer becomes a filter pipeline: parse → validate semantics → drop/repair structural violations → execute
- The pipeline is testable at each boundary without LLM involvement (unit tests cover repair logic; integration tests cover the LLM path)
- Test coverage must include "LLM returns structurally non-compliant response" scenarios with deterministic repair assertions
