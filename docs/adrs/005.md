# ADR-005: Deterministic Fallbacks for LLM Structural Non-Compliance

**Status:** Accepted  
**Supersedes:** None  
**Context:** Discovered during incremental compile dogfooding (May 2025)

## Decision

When an LLM structured-output response violates a structural invariant that the caller can resolve deterministically, **resolve it in code rather than retrying or failing**.

The LLM is trusted for creative/semantic work (synthesis, concept identification, relevance judgment). It is **not** trusted for structural compliance — even with explicit prompt instructions, JSON schema enforcement, and few-shot examples.

## Motivation

During incremental compile dogfooding, two systematic failures emerged across both `gpt-4o` and `gpt-4.1`:

### Example 1: New branches referencing only existing leaves

**Invariant:** In incremental mode, every new branch must include at least one newly-collected leaf.

**Observed behaviour:** The model consistently reorganises existing branches (creates new branches from old leaves) while ignoring the new leaf — especially when the new leaf is topically isolated from the existing cluster.

**Prompt attempts that failed:**
- "Only output branches that include at least one new leaf"
- Explicit `<new_leaves_to_integrate>` section listing slugs
- "If none fit any concept, return empty arrays"
- All three combined

**Deterministic fix:** Silently drop new branches whose leaf list contains no new leaf. The useful branches pass through; the irrelevant reorganisations are discarded.

### Example 2: Stale branches not addressed in response

**Invariant:** Every stale branch (referencing a deleted leaf) with ≥2 remaining leaves must appear in `updated_branches` with its rewritten body.

**Observed behaviour:** When multiple branches are stale, the model addresses some but consistently omits at least one — even when the prompt explicitly says "Branches marked stale MUST appear in updated_branches."

**Deterministic fix:** For unaddressed stale branches, remove the deleted leaf from their leaf list and preserve the existing body verbatim. The branch is repaired without LLM involvement.

## Principles

1. **Validate-then-fix, not validate-then-fail.** If the violation is mechanically resolvable (drop, filter, repair), resolve it. Only fail on violations that require semantic understanding to fix (malformed bodies, contradictory content, invented references).

2. **Never retry for structural compliance.** LLM non-determinism means the same structural violation may recur indefinitely. Retrying wastes tokens and time. If the fix is deterministic, apply it on the first pass.

3. **Prompt for intent, enforce in code.** The prompt communicates what the ideal response looks like. The code enforces what the response must satisfy. These are different concerns — prompt quality is best-effort optimisation; code enforcement is the contract.

4. **Log/surface dropped content at debug level.** Silent drops should be observable for diagnostics but should not produce user-facing noise. The user sees the result, not the LLM's missteps.

5. **The schema is necessary but not sufficient.** JSON schema prevents syntactic malformation. It cannot prevent semantic violations (wrong leaf references, reorganisation without integration, missing required entries). Post-parse validation + deterministic repair covers the gap.

## Applicability

This pattern applies whenever:
- The caller knows the complete set of valid states (e.g., valid leaf slugs, existing branch slugs, the set of new leaves)
- The violation can be detected by comparing the response against known-good data
- A reasonable default exists (drop, filter, use existing value)
- The semantic content of the response is still useful after the repair

It does **not** apply when:
- The violation is in the creative output (bad synthesis, hallucinated content)
- No deterministic resolution exists (the response is fundamentally unusable)
- The repair would silently change the semantic meaning of the output

## Consequences

- Compile succeeds on the first attempt in all observed real-world scenarios (previously required 3–5 retries or model switching)
- Prompt engineering becomes optimisation (better results) rather than correctness (system doesn't break)
- The validation layer becomes a filter pipeline: parse → validate semantics → drop/repair structural violations → execute
- Test coverage must include "LLM returns structurally non-compliant response" scenarios with deterministic repair assertions
